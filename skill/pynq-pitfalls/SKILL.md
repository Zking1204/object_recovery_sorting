# 零散但会咬人的 PYNQ 细节

> **归属**：`pynq/` 通用 PYNQ 技能 —— 换板卡、换题目都能用。
> 三条都是"知道了只要一行、不知道要查半天"的类型。

---

## Purpose

**目的**：把三类**"看起来像程序坏了、其实只是环境行为"**的现象，事先变成"理所当然"。

**预期产出**：

| 产出 | 说明 |
|---|---|
| 一个带超时的 `wait_bit` | 轮询不再挂死，超时消息里直接写排查方向 |
| 一条交付纪律 | 改了 `.py` 就去告诉需求方"要重启内核" |
| 三条环境事实 | `%run` 变量作用域 / `flush=True` / 重载 overlay 会熄屏 |

**前置条件**：无。

---

## When to Use

- 要写**轮询硬件状态位**的代码（等 IP 就绪、等 DMA 完成）
- **改了板端 `.py`**、要让需求方去跑
- 写**板端长脚本**（几十秒以上）

## When NOT to Use

- 桌面侧、不涉及 PYNQ/PL 的普通 Python —— 第一条仍成立，后两条不适用

---

## DO's

- 所有忙等循环**必须带超时**
- 超时**抛异常**而不是 `return False`
- **异常消息里直接写排查方向**（"检查参考时钟频率"这种）
- 改了 `.py` 之后，**主动**告诉需求方"要重新上传 + Restart Kernel"
- 长脚本**每一步 `print(..., flush=True)`**
- 交付前用 `hasattr` / 文件字节数**确认需求方真的加载上新版了**

## DON'Ts

- ⚠️ **不要把原厂 C 驱动的裸死循环直接翻译成 Python**
- ⚠️ **不要改完文件就让需求方跑** —— 需求方跑的是旧代码，白跑一轮还可能得出错误结论
- **不要省 `flush=True`**（否则输出卡在缓冲里，等于没打）
- **不要把"加载 overlay 后屏黑一下"当成坏了**

---

## Workflow：这三条怎么用

### Step 1：写轮询代码时 —— 一律用 `wait_bit` 模板（见第一节）
判据：把它指向一个**永远不会置位**的状态位，应在 `timeout` 秒后**抛异常**而不是挂住。

### Step 2：改了板端 `.py` 要交付时 —— 先声明再让需求方跑
判据：告诉需求方的三件事齐全 —— **① 改了哪个文件 ② 要重新上传 ③ 要 Restart Kernel**。

### Step 3：交付后自查 —— 确认需求方那边真的是新版
判据：`hasattr(mymod, '新函数名')` 为 `True`，且文件字节数与本地一致。

### Step 4：写板端长脚本时 —— 逐步 `print(..., flush=True)`
判据：中途失败时，日志里能看到**最后成功的那一步**。

## 一、所有忙等循环必须带超时

**适用场景**：任何轮询硬件状态位的代码。**失效条件**：无（硬要求）。

原厂 / 原工程的 C 驱动常写成裸死循环：

```c
while (!(Xil_In32(base + STATUS) & RUNNING));     /* ← 参考时钟不对就永远死在这 */
```

移植到 Python 时必须包成：

```python
import time

def wait_bit(mmio, off, mask, timeout=2.0, what="状态位"):
    t0 = time.time()
    while not (mmio.read(off) & mask):
        if time.time() - t0 > timeout:
            raise TimeoutError(
                f"{what} 超时 {timeout}s：寄存器 {off:#x} 的 mask {mask:#x} 始终为 0。\n"
                f"  排查方向：① 参考时钟频率对不对；② IP 是否被复位拉住；③ 地址是否写错"
            )
        time.sleep(0.001)
```

**三个要点**：① 有超时；② 超时**抛异常**而不是 `return False`；③ **异常消息里直接写排查方向**。

**已验证效果**：参考时钟不对时**立刻报错并提示"检查参考时钟频率"**，不再挂死。

**来源**：AI 早期写的 PC 侧测试桩**没有模拟 STATUS 行为**，桩自己把脚本**挂死 120 秒** ⇒ 才发现原驱动本来就有这个隐患。
**⇒ 这条经验其实是"用桩测驱动"测出来的，不是踩坑踩出来的。**

## 二、Jupyter 里换掉 `.py` 文件后，Python 不会重读

**适用场景**：任何在 Jupyter 里迭代 `.py` 模块的工作流（PYNQ 板端绝大多数工作都是这种）。**失效条件**：无。

换掉 `.py` 文件后，**必须**二选一：

```python
import importlib
importlib.reload(mymod)        # 方式一：重载
# 或 方式二：菜单 Kernel → Restart Kernel（更彻底，推荐）
```

**怎么确认真的加载上了**（别靠感觉）：

```python
print(hasattr(mymod, '新函数名'))          # 应为 True
import os; print(os.path.getsize(mymod.__file__))   # 和本地上传的比对字节数
```

**⇒ 一个稳妥的流程**：重新上传 `.py` → **Restart Kernel** → `%run cam_full.py`。
（纯 `reload` 在依赖链复杂时可能漏掉子模块；`%run` 的变量活在全局命名空间，**重启内核就会丢**。）

**已验证效果**：`reload` 后新函数可用；不 `reload` 时 `hasattr` 返回 **False**（说明确实在用旧版本）。

**来源**：AI 写完新函数就直接让需求方跑 ⇒ **实际使用中当场暴露**：

> "**你刚刚新写的东西我都还没加载上去呢，你就直接叫我开干了吗**"

**⇒ 结论：凡是"改了文件让需求方去跑"的场合，必须自己先说清"要重启内核/重载"，否则需求方跑的是旧代码，白跑一轮还可能得出错误结论。**

## 三、其它零散必知

| 事实 | 后果 | 做法 |
|---|---|---|
| `%run` 的变量在 Jupyter 全局命名空间里**跨 cell 可用**，但**重启内核后就丢** | 重启后接着用 `pz`/`ol` 会 `NameError` | 重启后**重新 `%run`**，别指望变量还在 |
| 板端长脚本若没有逐步输出 | 出问题就是"**卡住 + 零输出**"，完全无从下手 | 每步 `print(..., flush=True)`；`flush=True` 不能省（否则输出卡在缓冲里，等于没打） |
| PYNQ 加载 overlay 会**重载 PL** | 屏黑一下 | **正常现象**，别以为是坏了；同时也意味着**别在加载前访问 PL 地址**（见 `../pynq-overlay-load/SKILL.md`） |

**为什么把这三条放一起**：它们的共同点是 —— **都不影响功能正确性，但都会让你误判"程序坏了 / 卡死了 / 板子坏了"。**

## 来源（从哪些失败或观察中总结得出）

三条各有来历，**没有一条是"抄来的最佳实践"**：

1. **超时**：AI 早期写的 PC 侧测试桩**没有模拟 STATUS 行为**，桩自己把脚本**挂死 120 秒**
   ⇒ 才发现原驱动本来就有这个隐患。**这条其实是"用桩测驱动"测出来的，不是踩坑踩出来的。**
2. **Jupyter 不重读**：AI 写完新函数就让需求方跑 ⇒ **实际使用中当场暴露**
   > "**你刚刚新写的东西我都还没加载上去呢，你就直接叫我开干了吗**"
3. **`%run` 作用域与 `flush`**：板端长脚本出过一次"**卡住 + 零输出**"，无从下手 ⇒ 从此每步 `flush=True`。

**⇒ 共同点：这三条都不影响功能正确性，但都会让你误判"程序坏了 / 板子坏了"。**
