# 提示词工作流（W1~W11）

> **归属**：`workflow/` 工作流 —— **换任何项目都能用**。
> **比赛点名形式之一**：「一组**经过验证**、能稳定完成某类任务的**提示词模板及使用说明**」。
> 下面 11 条全部来自本项目真实协作，**原话照抄即可复用**。

---

## Purpose

**目的**：把"这次踩坑换来的说法"固化成**下次可以直接粘贴的模板**，让同一类错误不犯第二次。

**预期产出**：

| 产出 | 说明 |
|---|---|
| 一份模板库 | 11 条提示词，每条带**用途 / 模板原文 / 为什么有效 / 已验证 / 失效条件** |
| 一张场景对照表 | "我现在要做 X ⇒ 抄哪条" |
| 一套验收眼光 | 知道 AI 的交付物**少了哪一块**就该退回去重来 |

**前置条件**：无。这套模板本身就是起点。

---

## When to Use

- **要引入新东西**（算法 / 模块 / 工具 / IP）→ W1
- **要动工程文件、要启动长编译**→ W2（+ W10 如果改动依据是外部文档）
- **要写脚本改工程**→ W5
- **要给需求方一段他要自己跑的操作**→ W3
- **要拆一个做不完的大目标**→ W6
- **出现说不清的现象 / 改了没反应 / 缺少独立证据**→ W4 / W7 / W8
- **要交付代码给人接手**→ W9；**要交付 HDL 模块**→ W11

## When NOT to Use

- **一次性、无副作用的小事**（改地址、加一行打印）—— 套模板反而啰嗦
- **纯问答**（"这个 IP 是干嘛的"）—— 不需要方案书和工作流
- **改动依据本身就是权威规格**（芯片手册的时序参数）—— 以文档为准，不用 W10 对账

---

## DO's

- **先选场景，再抄模板** —— 别把 W1~W11 一起丢过去
- 抄的时候**把 `<>` 全部换成你自己的路径、名字、数字**
- 需求方提出一条新规则时，**回头审计已经交付的产物**是否也符合这条规则（本项目：需求方说"以后代码要逐行注释"，
  AI 回头一查，刚交付的三个 `.v` 全不合规 ⇒ 主动报出差距让对方决定是否重写）
- 每条模板后面**留住"为什么有效"** —— 那是这个模板值钱的唯一理由
- **规则升级了就改模板**（W1 后来追加了"每次讲算法都要说作用和重要性"，直接补进原条）

## DON'Ts

- **不要只记规则、不回头查已经交付的东西** —— 需求方说"以后"的时候，心里想的往往是**眼前这份**
- **不要把"报备过"当成"得到许可"** —— 见 W2，这条是拿一次整份回滚换来的
- **不要跳过"失效条件"** —— 一条没有失效条件的模板，换场景就是坑

## Workflow：怎么用这套模板

### Step 1：选场景

对照下面的场景表，找出**你现在正处在哪一格**。

| 你现在要做的 | 抄哪条 |
|---|---|
| 引入新算法 / 新模块 / 新工具 | **W1**、**W6** |
| 改动工程 / 启动长编译 | **W2**、**W5** |
| 改动依据是协作方契约 / 甲方规范 / 第三方工程 | **W10** → 再 **W2** |
| 给需求方一段他要自己跑的操作 | **W3** |
| 写脚本批量改工程 / 改文件 | **W5** |
| 现象说不清 / 改了没反应 | **W4**、**W7**、**W8** |
| 交付代码 / 交付 HDL 模块 | **W9**、**W11** |

### Step 2：照抄，替换占位符

把模板里的 `<文件路径>`、`<模块名>`、`<判据>` 换成你自己的。

### Step 3：检查 AI 的交付物**是否齐了**

每条模板的"产出"都是**有清单的**（比如 W2 要求方案书含"改哪个版本 / 只动哪些文件 / 耗时 / 副作用 / 验证 / 回滚"六项）。
**缺一项就退回去重来**，别将就。

### Step 4：拿"已验证 / 失效条件"当验收标准

## 模板库 W1~W11

### W1. ★ 四段式讲解：引入任何新东西之前先讲透

**用途**：引入新算法 / 新流水线级 / 新模块 / 新工具之前

**提示词模板**：
> 以后每次开拓一个新的算法的时候，你先要给我讲这个算法：
> **① 是干嘛的；② 能带来什么提升；③ 要注意什么；④ 优化的话能起到什么效果。**
> 讲完等我确认，再写代码。

**为什么有效**：强制 AI 在动手前把「设计意图 + 量化收益 + 已知风险 + 可选优化」一次摊开。
硬件上一次重编 6~25 分钟，**方向错了代价极高**，而"讲"的成本几乎为零。

**已验证**：讲完"灰度化"的四段后，需求方一次确认即进入实现，**无返工**。
**失效条件**：纯机械改动（改地址、加打印）不必套。

> ★ **2026-09-24 追加**：实践要求"**每次讲算法都要说一下对应算法的作用和重要性**"
> ⇒ 「作用 + 重要性」要**单独、明确地讲**，不能顺带提一句。

### W2. ★ 改动前先出方案书，并且**等一句"做"**

**用途**：任何要写盘 / 改工程 / 启动长编译的动作之前

**提示词模板**：
> 先给我一份改动方案，写清：**改哪个工程/哪个版本、只动哪些文件、具体改什么、预计耗时与副作用、怎么验证、怎么回滚**。
> **然后等我拍板，我说"做"你再动手。**

**为什么有效**：让需求方能在**零成本**阶段否决方案；也逼 AI 自己想清楚回滚路径。

**已验证**：之后每次大改动（拆帧差器、插算法槽位）都先出方案再动手，**零返工**。
**失效条件**：无副作用的小改可只作声明。

> ⚠️ **补丁（2026-09-24 深夜）**：**讨论过程中出现的方案性话语不构成开工许可。**
> 需求方在一轮讨论里说了"打一拍就行""既然打拍那么就是应该所有信号跟着一起打拍"，
> AI 当成许可直接改了 5 个源码文件并跑了编译仿真 ⇒ 需求方："**你在干嘛，我还没叫你动**"，全部回滚。
> ⇒ 只有明确的"**做 / 改 / 开始**"才算；"打一拍就行"这类只是**技术方向的确认**。

### W3. ★ 判据先行：每步都带成功/失败判据 + 排查分支

**用途**：给需求方任何一段要他自己跑的操作

**提示词模板**：
> 给我这一步操作时，同时给四样：① 这步在做什么、为什么、**为了确定或排除什么**；
> ② **成功判据**（看到什么现象算成功）；③ **失败判据 + 排查分支**；④ 需要我上传/重载什么文件。

**为什么有效**：把"做完之后怎么知道对不对"提前讲清；也逼 AI 想清楚"这一步到底在验证什么"。

**已验证**：板端每个 cell 都带判据后，需求方能自行判断结果，来回轮次明显减少。

### W4. ★ 反推测：先读源码/网表/头文件，再下断言

**用途**：任何"会不会卡 / 数据往哪走 / 谁触发谁 / 寄存器什么含义"的问题

**提示词模板**：
> 回答前先读 `<文件路径>` 的源码 / 网表 / 头文件，**用路径 + 行号作为依据**；
> 凡是拿不到证据的结论，**必须标注「推断」**。

**为什么有效**：硬件里"看起来应该会卡/不会卡"的推断极容易错，而错误结论会把排查带偏好几轮。

**已验证**：改用"先读源码"后，同链路上多个判断（是否直通、是否拴死）一次到位。

### W5. ★ 自检门禁式脚本

**用途**：写任何会修改工程/文件的脚本

**提示词模板**：
> 写一个脚本做 X。要求：① 每完成一步就打印一条自检结果；
> ② **任何一项自检不过就 `exit`，绝不写盘/保存**；③ 结尾打印可核对的摘要（改了什么、还剩什么、关键值）；
> ④ 脚本纯 ASCII。

**为什么有效**：把"失败"变成**无副作用的失败** —— 盘上文件保持原样，修完脚本再跑即可。

**已验证**：AI 的改动脚本曾因自己的 Tcl 语法错中途崩溃，**工程文件毫发无伤**；后续一次改动成功。

### W6. ★ 把大目标拆成"每步都能看见现象"的里程碑

**用途**：任何多级流水线 / 大型改动

**提示词模板**：
> 把这个大目标拆成 N 个里程碑，每个必须满足三条：
> ① 只引入**一点**新知识；② 完成后能在**屏幕 / 串口 / 寄存器**上看到明确现象；
> ③ 出错时能定位到**刚加的那一步**。

**为什么有效**：硬件上一旦出 bug，现象常常统一是"画面错行/黑屏"，级数一多就无法定位；
拆成有视觉判据的里程碑后，每一步都自证清白。

**已验证**：AI 想"一次做完八级流水线" ⇒ 意识到 8 级 = 8 个可能出 bug 的地方、且现象全一样 ⇒ 改成 5 个里程碑。

### W7. ★ 交叉验证：拿"已经工作正常"的兄弟模块反推

**用途**：某个点可疑、但缺少独立证据时

**提示词模板**：
> 对 `<可疑点>` 不要孤立判断。先找一个**已经正常工作**的同类模块，
> 对比它们在**同一组参数 / 同一根连线**上的差异。

**为什么有效**：省掉大量"从零推导"，且结论有工作实例背书。

**已验证**：两次直接定位到问题（"未连接输入必被拴成 1"、VTG 主从接反的真根因）。

### W8. ★ 先取基线，再判异常

**用途**：改动前 / 见到一堆报错时

**提示词模板**：
> 在改动之前，先对**未修改**的版本跑一遍同样的检查，把结果存成基线。
> 之后所有"异常"都要与基线对比，区分「**这次改出来的**」和「**本来就有的**」。

**为什么有效**：否则会把历史遗留报错当成自己引入的，或反过来把真问题当"一直都这样"放过。

**⚠️ 注意**：「基线也有」≠「可以不管」—— 本项目那条基线的报错后来查明是上次回滚残留，**是真 bug**。
**已验证**：基线法成功把"这次改出来的错"与残留错分开。

### W9. ★ 逐行注释：让人能接手的代码

**用途**：任何"AI 出稿、人 review 或长期维护"的代码

**提示词模板**：
> 以后自研代码要有**逐行注释**：
> 每一行有实际功能的代码**行尾**都跟一条注释，说明**这行在做什么、为什么这么写**；
> 纯声明、空行、`end` / `endmodule` / `begin` 之类可以省。
> 工程里**继承来的**代码不在此列，不要动。

**为什么有效**：
凡是要**人接着往下改**的代码（不是一次性脚本），看懂的成本才是主要成本。
AI 写的代码"能跑"不等于"能维护"——逐行注释把 review 成本从"逐句反推意图"降到"扫一遍确认"。
尤其 HDL：一个位宽错、一拍延迟错，现象往往只是"画面不对"，没有注释就只能靠反推。

**已验证**：本项目顶层与两个检测子模块要由**两个不同的人各自维护**，
注释密度直接决定对方接手时要不要重问一遍设计意图。

**失效条件**：一次性丢弃的调试片段、自动生成的代码不必套。

### W10. ★ 拿到外部文档（契约/规范/别人的设计）先与现状对账，不要照做

**用途**：拿到协作方的分工契约、甲方给的接口规范、第三方工程说明时

**提示词模板**：
> 这是 `<文档名>`，你先**和工程现状对一遍账**：
> ① 文档里哪些**已经做完了**（给出证据）；
> ② 哪些和**现有实现冲突**（冲突以现状为准）；
> ③ 哪些是**文档本身的缺陷或没定义清楚**的地方；
> ④ 文档的"待确认事项"你能直接结掉几条。
> 然后告诉我**照做之前需要改文档里的哪几条**。

**为什么有效**：
外部文档通常写得比现状"理想"，直接照做会把已经跑通的东西推倒重来；
而对账能一次性暴露"文档缺信号""地址撞车""标注不准"这类**合体那天才爆**的问题。

**已验证**：本项目从协作方的分工契约里当场查出 4 个问题（帧尾信号缺失、格式标注错误、寄存器地址撞车、分辨率混淆），
并直接结掉契约里 2 条"待确认事项"。详见 `../CHANGELOG.md`。

**失效条件**：文档本身就是权威规格（如芯片手册的时序参数），以文档为准。

### W11. ★ 写完 HDL 先写自检式 testbench，**跑仿真再往下走**

**用途**：任何 HDL 模块写完之后、上板之前

**提示词模板**：
> 写完这个模块，**再写一个自检式 testbench**（自己比对、自己报 PASS/FAIL），跑仿真确认算得对。
> 期望值要**手算**，不能拿模块自己的公式去算（那是循环论证，公式错了两边一起错）。
> 边界值优先：`0`、最大值、**刚好相等**（测 `>` 还是 `>=`）、**刚好进位/截断**。
> **不用综合** —— `xvlog` + `xelab` + `xsim` 三步就能跑。

**为什么有效**：
`xvlog`/`xelab` 只能证明"语法合法、位宽自洽、连接对"，**证明不了算出来的数对不对**；综合也一样。
仿真能验证**行为**，而且不需要等位流（**几秒钟出结果**）。

**已验证**：本项目里程碑 1 写了三个 testbench、共 40 个用例，
**第一次跑就抓出一个只看代码发现不了的真 bug** —— 帧首那个像素用了**上一帧**的参数。
它只占一帧 70 万个像素里的**一个**，**上板肉眼绝对看不出来**，
但会让"刚关掉使能"那一帧的计数和标志位整个带偏。

**失效条件**：纯连线/纯例化的模块没什么可测的。

**配套技能**：怎么写这套 testbench 见 [`../testbench-guide/SKILL.md`](../testbench-guide/SKILL.md)。

## 已验证效果（汇总）

| 模板 | 验证结果 |
|---|---|
| W1 四段式 | 讲完即确认，**无返工** |
| W2 方案书等"做" | 大改动零返工；**但"讨论中的方向≠许可"这条是回滚一次换来的** |
| W5 自检门禁 | 脚本崩过一次，**工程文件毫发无伤** |
