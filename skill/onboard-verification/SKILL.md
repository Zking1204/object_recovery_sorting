# 上板验证：怎么用数字证明一个功能真的在工作

> **归属**：`workflow/` 跨项目通用。
> 是 `../verification-methods/SKILL.md`（不靠猜地定位）的**真板版本**：那里解决"现象说不清"，
> 这里解决"**只有几个寄存器可读，怎么排除掉所有别的解释**"。

---

## Purpose

**目的**：把"我加的功能好像有用"变成"**有数字、且排除了其他解释**"。

**为什么难**：真板上既没有波形，也没有断点。你手里通常只有：

- 一个可以开关的配置位
- 一个可以读回的数字（计数 / 状态 / 时间戳）

而**错误结论几乎总是从这两样东西的错误解读里出来的**。

**预期产出**：

| 产出 | 说明 |
|---|---|
| 一张 A/B 对比表 | 含**可信度判据**（哪些行作废、为什么） |
| 一句可写进报告的结论 | "该功能生效，量化效果 = X%" |
| 该功能的**适用边界** | 什么场景下它有用、什么场景下它本就不该有变化 |

**前置条件**：能确认"板上跑的确实是你要验的那一版"（版本号 / 位流 MD5 / 固件哈希）。

---

## When to Use

- 刚给板子/设备加了一级新功能，要确认它**真的接进去了**
- 要做"开 / 关某个开关"的效果对比
- **上板数据和预期完全不符**（先怀疑测量方法，再怀疑被测对象）
- 要把"优化了多少"写成报告里的数字

## When NOT to Use

- 逻辑定位阶段 —— 那应该在仿真里做（`../testbench-guide/SKILL.md`），比在板上试快 100 倍
- 指标本身没有读出通路 —— 那要先加一个可读寄存器，而不是硬看现象
- 被测对象的方差远大于待测效应 —— 那要先提高信噪比，测了也是白测

---

## DO's

- **先把"判据"写成一句话，再写代码**：这句话里必须包含"**在这个场景下**"这个限定
- **确认版本**：MD5 / 版本号 / 构建号，**写进同一段输出里**，别凭记忆
- **三明治 A/B/A**：测 A → 测 B → 再测 A。**两次 A 的差就是"被测对象自己漂了多少"**
- **选一个"低于饱和线"的工作点**：让读数落在量程中段
- **造一个"该功能唯一擅长"的测试场景**（可控测试卡 / 合成输入），而不是碰运气找一个
- **把作废的行明确标出来**，别让它们混进结论

## DON'Ts

- ⚠️ **不要把"计数变了"当成"功能生效了"** —— 除非你能排除"是别的因素在变"
- ⚠️ **不要忘了计数器可能是饱和的**：读数顶到上限时，它表示"**≥ 上限**"，不是"等于上限"
- ⚠️ **不要在中途改变场景**（换光照、挪物体、遮挡/放开）—— 前后数据立刻不可比
- ⚠️ **不要用一个"通用判据"**去验证一个"只在特定条件下才起作用"的功能
- ⚠️ **不要只看一次读数** —— 帧级/周期级指标本身就是波动的，要多次取样取中位数

## Workflow

### Step 1 — 确认板上是你要验的那一版

**产出**：一行可核对的身份信息（位流 MD5 / 版本号）。
**判据**：和构建产物对得上。对不上就**停下来**，后面全是白做。

### Step 2 — 写下判据，并检查它有没有"限定条件"

```
❌ 差判据：打开中值以后，目标计数应该明显变小
✅ 好判据：在【命中的是孤立小点】的场景下，打开中值后计数应下降 60% 以上；
          在【命中的是大片连续区域】的场景下，计数【本来就不该变】——那不是失败
```

**判据的检验方法**：把这句话反过来问一遍 ——
**"如果功能没生效，会不会也观察到同样的结果？"** 如果答案是"会"，判据不合格。

### Step 3 — 找/造一个合适的场景

优先**造**，不要**找**：

| 想要测的 | 造法 |
|---|---|
| 中值/滤波去孤立噪点 | 黑底 + 几个大小递增的白点（手机屏幕当可编程测试图）／白纸 + 记号笔点黑点 |
| 面积/形状统计 | 已知尺寸的方块阵列 |
| 阈值/二值化 | 灰阶条 / 已知灰度的手工卡 |

**为什么必须造**：自然场景里"命中的像素"往往是成片的真实景物，
用它测"去孤立点"的功能，**功能正确地什么都不做**，而你会误判成"没生效"。

### Step 4 — 三明治 A/B/A + 取样

```
A1 = 关（多次取中位数）
B  = 开（多次取中位数）
A2 = 关（多次取中位数）

漂移 = |A2 - A1| / max(A1, 1)
效果 = 1 - B / A1
判定 = 可信  若 漂移 远小于 |效果|
      作废  若 漂移 与 效果 同量级
```

**为什么必须 A2**：A/B 两次测量之间**任何东西都可能变**——
光照、被测物自己在动、自动增益在爬、甚至你自己把遮挡物挪了。
**A2 是唯一能把这些暴露出来的东西。**

### Step 5 — 扫一条曲线，而不是测一个点

单点对比最容易骗人。**扫一条自变量曲线**（阈值 / 半径 / 频率），同时画 A 和 B：

- 两条曲线**完全重合** ⇒ 功能没生效（或这个自变量范围里它不该有作用）
- 两条曲线**在某段分开** ⇒ 那一段就是它的作用区间，**把区间读出来**
- **单调性被破坏**（比如"阈值升高但计数反而变大"）⇒ **数据不可信，先查场景是不是变了**

### Step 6 — 反过头做一次"必然成立的边界自检"

用两个**理论上必然**的值把整条读数链路串起来验，例如：

- 让判定条件恒不成立 ⇒ 读数必须**恰好为 0**
- 让判定条件恒成立 ⇒ 读数必须**恰好等于上限**（注意饱和！）

**这一步的价值**：它把"读数链路本身对不对"和"算法对不对"彻底分开。

## 已验证效果（本项目实测）

| 场景 | 观察 | 结论 |
|---|---|---|
| 版本身份 | 板上位流 MD5 = 刚构建的那份 | ✅ 排除了"跑的是旧版本" |
| 边界自检 | 判定条件恒不成立 ⇒ 计数 **0**；恒成立 ⇒ 计数 **65535（16 位饱和上限）** | ✅ 读数链路正确（**注意这里是饱和，不是 696,460**） |
| 孤立特征场景 | 中值开 ⇒ 白斑从"全在"变成"**小于 4 个像素的消失**" | ✅ **功能生效**（肉眼+数字双证） |
| 连续区域场景 | 中值开/关 ⇒ 计数比 **0.97 ~ 1.01** | ✅ **本来就该不变**（不是失败） |
| 中途改场景 | 同一阈值下先测出 0、后测出 3212 ⇒ **单调性被破坏** | ❌ 该段数据作废，原因是"遮挡物中途被放开" |

**最有用的一条副产品**：在"孤立特征"场景里量出的**抹除尺寸**
（"小于 4 个像素的斑点被抹掉"）直接变成了设计决策的依据。

## 来源（从哪些失败或观察中总结得出）

1. **判据写错那次**：我给的判据是"打开中值后目标计数应明显变小"。
   实测 `21987 → 21921`（差 0.3%，在噪声里），我据此报"❌ 中值没生效"。
   **需求方没有质疑代码，而是继续按我给的方向测**；我随后才算明白：
   那张图有 **3.16% 的像素**超过阈值，是**成片的真实景物** ——
   **中值正确地什么都不做**。判据本身才是错的（少了"在这个场景下"这个限定）。
2. **饱和那次**：扫描阈值时 `th = 0…200` 全是 `65535`，我把"65535 ÷ 总像素"当成命中比例，
   算出"9.41%"，还据此下了结论。实际上**那是 16 位饱和计数的上限**，
   真实值是"≥65535"，信息量为零。
3. **单调性被破坏那次**：同一张表里 `th=16` 读 0、`th=32` 读 3212 ——
   **"大于 32 的像素必然大于 16"**，两者不可能同时成立。
   追下去是**需求方中途把手从镜头上放开了**。这条自相矛盾是整轮测试里最有价值的信号。
4. **三明治测法的由来**：上面第 3 条如果一开始就做了 A/B/A，**第二次 A 会自己把漂移暴露出来**，
   不用等人去发现矛盾。
