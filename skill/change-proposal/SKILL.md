# 改动方案书模板

> **归属**：`workflow/` 工作流 —— 换任何有长耗时构建的工程都能用。
> 配合提示词 **W2**（改动前先出方案、等一句"做"）。

---

## Purpose

**目的**：让需求方**在零成本阶段**就能否决一个坏方案 —— 而不是等改完、编译完再回滚。

**预期产出**：

| 产出 | 说明 |
|---|---|
| 一份方案书 | 七个固定小节，见下方模板 |
| 一条纪律 | **报备 ≠ 许可**；等一句明确的"做" |
| 一条回滚路径 | 方案书里必须写出来，而且**已经真的备份过** |

**前置条件**：你已经知道"要改什么"，但**还没有动任何文件**。

---

## When to Use

任何满足以下**任一条**的动作之前：

- 要**修改工程文件**（工程文件集 / BD / 约束 / 源码）
- 要**启动长耗时构建**（综合、实现、编译）
- 要**覆盖交付物 / 重载硬件**

## When NOT to Use

- **无副作用的小改**（只读、只打印、只加注释）—— 声明一句即可
- **纯讨论**（"如果这样做会怎样"）—— 那是在出主意，不是在提方案
- **改动依据是权威规格**（芯片手册给死的时序参数）—— 直接照做，不用七节方案

---

## DO's

- 方案书里**必须写"改哪个工程 / 哪个版本"** —— 需求方真的会问"**你是在哪个版本上改**"
- 方案书里**必须写"预计耗时"** —— 需求方真的会问"**需要多久**"
- 方案书里**必须单独列一节"明确不动的东西"** —— 让需求方放心
- 每一步都给**成功判据 + 失败说明什么**
- **先备份再动**（整目录 + 交付物各一份）
- 方案书写完**停下来等**，直到听到"**做 / 改 / 开始**"

## DON'Ts

- ⚠️ **不要把"我已经报备过了"当成"我可以动手了"** —— 这条是拿一次**整份回滚**换来的
- ⚠️ **不要把讨论中的方案性话语当成许可**。需求方在一轮讨论里说"打一拍就行""3×3 还是要做的"，
  那是**技术方向的确认**，不是开工许可。只有明确的"做 / 改 / 开始"才算。
- **不要只写"改什么"不写"不动什么"** —— 后者才是让人敢点头的部分
- **不要漏掉回滚路径**，也不要写一条**没验证过**的回滚路径

## Workflow

### Step 1：先备份（在写方案之前就要想清楚备份路径）

| 备份什么 | 习惯路径 |
|---|---|
| 整个工程目录 | `_bak_<工程名>_<日期><序号>` |
| 交付物 | `<文件名>.bak_before_<改动名>` |
| 关键源文件 / 约束 | 同名 `.bak_*` |

**回滚一律从备份还原，禁止凭记忆改回去。**

### Step 2：写方案书（照抄下面的模板填空）

### Step 3：**停下来等一句"做"**

在这一步之前，**一个字都不许写盘**。需求方说"停"就停、说"回滚"就回滚。

### Step 4：按方案书执行，每一步做完就报判据

### Step 5：验证（每一步都有自己的判据，见方案书第 5 节）

### Step 6：留痕

把"改了什么、结果如何"追加进 `../CHANGELOG.md`。

## 方案书模板（照抄填空）

```markdown
# 改动方案：<一句话标题>

## 0. 一句话总览
改 <几个> 个文件 / <几个> 个 cell，<要不要重编>，预计 <多长时间>。

## 1. 改动清单
| # | 改什么 | 具体位置（完整路径） | 为什么 |
|---|---|---|---|
| ① | | | |
| ② | | | |

## 2. 改前 → 改后（图示或连接表）
<用代码块画连线/结构的前后对比>

## 3. 明确不动的东西（让需求方放心）
- ✗ 约束文件一行不动
- ✗ 其余 N 个模块不动
- ✗ …

## 4. 执行步骤与时间
| 步骤 | 内容 | 时间 |
|---|---|---|
| 0 | 整目录备份 | |
| 1 | 改动（脚本 + 自检） | |
| 2 | 自检 → **先只跑这一步，结果给需求方看** | |
| 3 | 全量编译 | |
| 4 | 交付 + 校验 | |

## 5. 验证判据（每步都要有）
| 阶段 | 判据 | 失败说明什么 |
|---|---|---|
| 自检后 | | |
| 编译后 | | |
| 上板后 | | |

## 6. 风险与回滚
| 风险 | 应对 |
|---|---|
| <已知会踩的坑> | |
- **回滚路径**：整目录备份 `<路径>`；交付物备份 `<路径>`

## 7. 需要你现在拍板的事
- 决策 1：<选项 A / B，各自代价>
- 决策 2：<…>
```

## 为什么必须这样写（三条硬道理）

| 要求 | 道理 |
|---|---|
| **写"改哪个工程/哪个版本"** | 需求方实际会问："**你是在哪个版本上改**" |
| **写"预计耗时"** | 需求方实际会问："**需要多久**" |
| **写"只动哪些文件"+"不动哪些"** | 让需求方能在**零成本**阶段否决，而不是改完再回滚 |

## 特例：外部文档（契约/规范）驱动的改动 —— 对账先行

当这次改动的依据是**别人给的文档**（协作方的分工契约、甲方规范、第三方工程的说明），
方案书里必须先加一节**对账**，再谈改动：

| 对账项 | 要回答什么 |
|---|---|
| **已完成** | 文档要求的哪些**现状已经有了**？（给出路径/寄存器/实测证据） |
| **冲突** | 哪些和现有实现矛盾？**冲突以现状为准**，并写明为什么 |
| **文档缺陷** | 文档本身哪里**没定义清楚**或**写错了**？（缺信号、地址撞车、格式标注不准…） |
| **能结掉的疑问** | 文档列的"待确认事项"里，哪几条现在就能给出答案？ |

**⇒ 对账做完再写"改动清单"** —— 否则会把已经跑通的东西推倒重来。

**真实案例**：本项目从协作方的分工契约里当场查出 4 个问题，并结掉契约自己列的 2 条待确认事项。
详见 `../CHANGELOG.md`；对应提示词 **W10**。

## 来源（从哪些失败或观察中总结得出）

**一次"报备过两次"就直接动手的教训**：AI 自认为已经把"改哪个文件、改成什么、为什么"列清楚了，
就擅自改了 BD、加了源文件、重新编译 ⇒ 当即被要求**整份回滚**——"从始至终我都没叫你动"。

**⇒ 结论：报备 ≠ 许可。方案书写得再细，也要等一句明确的"做"。**

**第二次（2026-09-24 深夜）**：AI 把讨论里的"**打一拍就行**"当成许可，直接改了 5 个源码文件并跑了编译仿真
⇒ 需求方"**你在干嘛，我还没叫你动**"，5 个文件全部还原。
**⇒ 补充结论：讨论中出现的方案性话语，只是技术方向的确认，不构成开工许可。**
