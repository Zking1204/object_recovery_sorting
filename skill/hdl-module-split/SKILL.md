# HDL 模块化与数据流接口约定

> **归属**：`workflow/` 工作流 —— **换任何 FPGA/HDL 工程都能用**。
> 本文件是从一个真实的多级图像流水线项目里总结出来的，不是教科书抄的。

---

## Purpose

**目的**：让**多级算法**这种必然会很长的东西，在**还很便宜的时候**就把结构定死 ——
因为 HDL 里"先跑通再重构"要付综合、时序、上板验证各一遍的代价。

**预期产出**：

| 产出 | 说明 |
|---|---|
| 一个只做例化的顶层 | 一条流水线一眼看完 |
| 每级一个文件 | 可单独仿真、单独看资源、单独切出来看 |
| 一套统一接口 | 插入新级时**不改邻居** |
| 三条打拍纪律 | 见下文「打拍时怎么写才对」 |

**前置条件**：你知道这条流水线大概有几级（哪怕只是估个数量级）。

---

## When to Use

- 一个模块里要串**多级算法**（每级几十行到上百行），最终会很长
- 会有**第二个人**接手或并行开发
- 需要**逐级定位问题**、逐级看资源
- **要给某一级插流水寄存器**（时序收不敛时）
- **要给某一级加行缓冲 / FIFO**（这时必然产生非整数拍延迟）

## When NOT to Use

- **单文件几十行的小设计** —— 拆了反而更难读
- **纯组合的一小段逻辑** —— 不必拆
- **一次性验证脚本里的模块** —— 不会有人接手

---

## DO's

- **顶层只做「例化 + 连线 + 汇总」，一行算法都不写**
- **一级一文件**，文件名 = 模块名
- **模块名加前缀**（Verilog 模块名全局唯一，两人并行迟早撞车）
- **每级的接口长得一模一样**（`in_valid/in_data/in_sof/in_eol/in_eof` → `out_*`）
- 打拍时**五根信号无条件一起进寄存器**
- 下游统计**只用"自己这一级的 sideband"**
- 控制信号用**这一级自己的 `sof`** 锁存
- 把「统计 / 计数 / 上报」这类辅助逻辑**用寄存器从主数据链上隔开**

## DON'Ts

- ⚠️ **不要把视频/数据通路的延迟线塞进某一个算法模块** —— 那会让算法模块从"纯旁听者"变成通路的一部分，
  以后每改一次算法都有机会弄坏主通路。**这类"通路级"的东西归顶层。**
- **不要写 `if (in_valid)` 之类的门控去打拍** —— 不需要，而且是错的写法
- **不要跨级引用上游信号**（拿第 0 级的 `px_valid` 去门控第 5 级）
- **不要在像素通路上组合地直接用控制信号** —— 会出现"半屏一个阈值"的撕裂
- **不要为了打拍而打拍** —— 每级寄存器有固定开销（clk-to-Q + setup ≈ 0.5 ns），还会加重布线拥塞

---

## Workflow

### Step 1：先定前缀（在写第一行代码之前）

**Verilog 的模块名是全局唯一的** —— 两个人在同一个工程里各写一个叫 `linebuf` 或 `gray` 的模块，直接撞车。

**⇒ 约定**：每人一个前缀（本项目：定位链 `dd_`、尺寸链 `sd_`）。**这条必须写进分工契约。**

### Step 2：定统一接口（一次定死，之后每级照抄）

```verilog
module xxx_stage (
    input  wire        clk, rst_n,
    // 输入
    input  wire        in_valid,
    input  wire [N-1:0] in_data,
    input  wire        in_sof,     // 帧首 / 包首
    input  wire        in_eol,     // 行尾
    input  wire        in_eof,     // 帧尾
    // 输出
    output wire        out_valid,
    output wire [M-1:0] out_data,
    output wire        out_sof,
    output wire        out_eol,
    output wire        out_eof
);
```

### Step 3：顶层只例化

```
xxx_top.v            ← 例化 + 流水线串联 + 结果锁存
    ├── xxx_stage1.v ← 第①级
    ├── xxx_stage2.v ← 第②级
    └── xxx_stage3.v ← 第③级
```

**⇒ 直接后果**：以后每加一级 = 多一个文件 + 顶层多一行例化，**老代码一行不用动**。

### Step 4：每级写完立刻单独仿真

见 `../testbench-guide/SKILL.md`。

### Step 5：需要打拍时，按下面三条纪律写

---

## ★ 核心原则

### 1. 顶层只做「例化 + 连线 + 汇总」，**一行算法都不写**

**好处（按重要性排）**：

| 好处 | 为什么重要 |
|---|---|
| **每级能单独写 testbench 仿真** | 几百行的模块没法单独测；几十行的可以 |
| **综合后能单独看资源** | "中值滤波占多少 LUT" 只有拆开才答得出来 |
| **出问题能一级一级切出来看** | 把中间结果引到屏幕上，一眼定位是哪级错 |
| **才可能逐行注释得清楚** | 上千行的文件谁都读不动 |

### 2. 接口长一样

**好处**：任何一级都能被单独例化、单独仿真、单独替换；插入新级时不用改邻居。

---

## ★★ 最核心的纪律：sideband 必须跟数据同步延迟

> **`valid` / `sof` / `eol` / `eof` 必须和数据一起延迟同样的拍数，一道都不能少。**

| 漏哪一根 | 后果 |
|---|---|
| `valid` | 多算/漏算数据 |
| `sof` / `eof` | **帧边界错乱** |
| `eol` | **行边界错乱** |

**而且症状很难查**：屏幕上通常只表现为"画面整体偏移"或"对不上"，看不出是哪一级漏的。

**⇒ 所以模块边界的选择要跟着这条纪律走：**

| 做法 | 延迟 | 对齐风险 | 代价 |
|---|---|---|---|
| **纯组合（0 拍）** | 0 | ✅ **天然对齐，不可能错** | 关键路径逐级累加 |
| **打 1 拍** | 1 拍 | ⚠️ 要同步延迟 5 根信号 | 缩关键路径，多一个出错点 |

**实战取舍**：如果这段流水线总路径**放得进时钟周期**（例如 3 个加法器 ≈ 3–4 ns，而周期是 10 ns），
**就先用纯组合** —— 把"对齐"这个最容易错的问题直接消灭掉。
等到某一级**不得不**要存储器（行缓冲、FIFO）而必须打拍时，再一起做同步延迟。

---

## 打拍时怎么写才对（三条，都是踩出来的）

### ① 五根信号无条件一起进寄存器，不要写 `if (valid)` 之类的门控

```verilog
always @(posedge clk) begin
    if (!rst_n) begin
        r_valid <= 1'b0; r_data <= 0; r_sof <= 1'b0; r_eol <= 1'b0; r_eof <= 1'b0;
    end else begin
        r_valid <= in_valid;  r_data <= d;      // ★ 无条件，不看 valid
        r_sof   <= in_sof;    r_eol  <= in_eol; r_eof <= in_eof;
    end
end
```

*为什么不需要门控*：下游反压时上游会把**同一个数据重复送好几拍**，但那几拍 `valid`（= `tvalid & tready`）是 0，最后一拍才变 1。
五根一起打拍，下游看到的仍然"只有一拍 valid"，既不会漏也不会数重。
反过来，**只延迟数据、不延迟 `valid` 才是错的** —— 那才会错位。

### ② ★ 下游必须用"自己这一级的 sideband"，绝不能混用上游的

插了一级寄存器之后，下一级的 `in_*` 已经比外部的 `px_*` 晚 N 拍了。此时统计逻辑如果还拿外部的 `px_valid` / `px_sof` / `px_eof` 去配对，
就会出现**每帧 ±1 的静默错误**：

| 错配 | 后果 |
|---|---|
| `hit_now = px_valid & t_hit` | 空拍（消隐/反压）之后第一个数据**多算一个**（此时 `t_hit` 还是上一拍的残值） |
| 帧首清零用 `px_sof` | 空拍之前最后一个数据**漏算** |
| 帧末用 `px_eof` 驱动影子寄存器 | 影子寄存器**早一拍**搬运，**永远少算最后一个数据** |

**症状：屏幕上完全看不出来，只能靠仿真抓。**
（对应的 testbench 用例：在帧中间故意插两拍空拍，数出来的命中数必须不多不少 —— 见 `../testbench-guide/SKILL.md`。）

> **一句话规则：下游永远拿"自己这一级的 sideband"配"自己这一级的像素"。**

### ③ 控制信号（阈值 / 极性 / 使能这类"每帧一个值"的慢变量）不需要打拍

它们是**准静态量**，只要在**使用它的那一级**、用**这一级自己的 `sof`** 锁存一次即可：

```verilog
always @(posedge clk) begin
    if (!rst_n)      th_cur <= 8'd0;
    else if (in_sof) th_cur <= cfg_th;      // ★ 用"这一级看见的帧首"，不是外面的 px_sof
end
```

*为什么链再深也自动对齐*：**帧首本身也在流水线里走** —— 链深了帧首也晚，参数锁存跟着一起晚，
所以"参数在哪一拍生效"的答案永远是同一个：**这一帧的第一个数据**。
*代价*：参数生效最晚晚一帧（"下一个帧首"最晚要等一帧才来），做自动扫参数时按这个速率规划。

> ⚠️ 唯一禁止的写法：**在像素通路上组合地直接用控制信号** —— 那样改参数的那一拍会落在画面中间，
> 出现"上半屏一个阈值、下半屏另一个"的撕裂。

---

## ★ 时序：**辅助逻辑不要串在主数据链上**

拆完模块之后，最容易犯的时序错误不是"某一级太复杂"，而是：

> **把「统计 / 计数 / 饱和判断 / 上报」这类辅助逻辑，和主数据链串在同一个组合路径上。**

### 真实案例（2026-09-24）

算法链只有 3 个加法器 + 1 个比较器（约 5ns），本身很轻松。但帧内统计写成了**组合**：

```
输入寄存器 → 3 个加法器 → 比较器 → hit → 32位加法 → 32位饱和比较 → 影子寄存器
                                        └──────── 数据路径 11.42ns ────────┘
                                        （要求 10ns，Slack −1.677ns）
```

**综合报 17 条时序违反，全部是同一条路径** —— 算法的终点不是"算完了"，而是"顺手把计数也算完并锁存"。

### 修法：**把那条路径整个消灭，而不是去优化它**

| 步 | 做法 | 效果 |
|---|---|---|
| ① | 计数器从 **32 位** 降到 **16 位饱和** | 32 位加法和 32 位比较**一起消失** |
| ② | 影子寄存器改成比帧末脉冲**晚一拍**锁存 | 那一拍计数器里自然已含最后一个数据 ⇒ **根本不需要那个组合的中间值** |

**结果**：算法链的终点只剩一个寄存器的 **CE（时钟使能）**，和计数器彻底分开。

### 通用判据

> 画一下这条路径的起点和终点。如果**终点是个"统计 / 上报 / 状态"寄存器**，
> 而它中间又夹着主数据链 —— **先问一句"这条路径真的必须组合吗？"**
> 答案往往是不必须：**晚一拍用寄存器隔开**就行，代价是 1 个寄存器和 1 拍延迟。

## 已验证效果

本项目把这套用在一个多级图像流水线上：

- 第一级（灰度）和第二级（二值化）拆成两个文件，顶层只留例化和统计；两级都做成**纯组合**
- `px_hit`（算法输出）与 `px_data` **严格同拍**，**完全没有对齐问题**
- 两级各自能单独写 testbench，**首次仿真就抓出了一个只看代码发现不了的 bug**（见 `../testbench-guide/SKILL.md`）
- 时序打穿后按"辅助逻辑用寄存器隔开"的判据改，**WNS 从 −1.677ns 回到 +0.511ns**

---

## ★★ 双支路合并：参数逐字相同 + 下游只用"对齐之后的"那一份（2026-10-11 实测）

两条支路各算各的、最后合并（本项目 A = 灰度阈值 ／ B = Sobel → 取或），**两个坑一次踩全**：

1. **各支路自己例化"补偿延迟"的模块时，参数必须逐字相同。**
   本项目那次踩的坑：A 支路的延迟补偿模块传 `COLS = AL_COLS`，B 支路那份写成 `COLS = LB_AL_COLS - 1`
   ⇒ **两条支路差 1 拍** = B 支路的判定**整体右移一列**。现象极规整：Sobel 本应在第 5/7 列命中，DUT 落在第 4/6 列。
   ⇒ 参数放**唯一真相源**（顶层 parameter），两处都引用它；改一处必须同步另一处。
   （注：举这个例子的那一版模块已于 2026-10-10 整版清退 —— **这条纪律与具体模块无关，照样成立**。）
2. **合并点与下游必须用"对齐之后"的那一份信号。**
   显示支路用的是 `t_hit | s_hit_d`（对齐后），送进形态学的却写成 `t_hit | s_hit`（**原始**）
   ⇒ 计数、判 flag、最终图像用的掩膜，把"像素 P 的 A 判定"和"像素 P+1 的 B 判定"或在一起 ——
   **屏幕上根本看不出来的错位**，只有逐像素比对才抓得到（实测 32 条错 + 帧计数 20 vs 30）。

**判据**：合并前先做一次**单点单拍标记**，分别量两支路各自的 LAT，**相等才算对齐**；
合并后**同一个信号名只允许出现一次**（要么用原始、要么用对齐后，不能两处各用各的）。

## 来源（从哪些失败或观察中总结得出）

**触发**：算法刚写到第 2 级、准备往第 6 级写的时候，需求方问：

> "**你不可能把所有算法写进我哪个模块吧，应该是在里面例化吧**"

**⇒ 当时顶层已经把 2 级算法塞在同一个文件里了。** 越往后越贵：6 级再拆就是大手术，2 级拆只是搬两段代码。

**沉淀的教训**：
1. **"先跑通再重构"在 HDL 里代价很高** —— 综合、时序、上板验证全部要重做一遍，所以结构要**尽早定**
2. 需求方提出这个问题的时机正好是*最便宜*的时候，**说明结构问题应该主动想，而不是等它变成问题**
3. 命名前缀这条是**推**出来的（Verilog 模块名全局唯一 + 两人并行开发 = 迟早撞车），
   但项目里还没真的撞过 —— **标为"预防性约定"，不是踩坑总结**
4. **「打拍三条纪律」是 2026-09-24 那次流水线讨论总结出来的**（其中②那条错配的后果，
   由 testbench 的"空拍用例"实测确认）
