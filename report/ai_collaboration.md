# 大模型协作记录（详细版）

本文件是设计报告第 7 章的展开，记录本项目在**提示词设计、错误建议的识别与处置、自我纠错轨迹、验证与判别方法、工具链使用**五个方面的完整过程。设计报告只给结论，这里给过程与原始判据。

---

## 0 协作模式：约束工程

整个项目按"**先立约束、再分段放行**"的方式与大模型协作，而不是"提一个需求、等一个交付"。

| 环节 | 做法 |
|---|---|
| 目标约束 | 先把不可让步的边界写清：单块 PYNQ-Z2、100 MHz、器件 `xc7z020clg400-1`、工具链固定 2026.1、PL 承担全部逐像素运算、PS 侧走 PYNQ 不走裸机 |
| 阶段门 | 每个阶段先定"放行判据"，达标才进入下一阶段（见 §5） |
| 反向验证 | 大模型给结论时，同时要求给"这个结论依赖哪些前提"，逐条核实前提而不是重复结论 |
| 留痕 | 每一轮改动记录"改了什么 / 判据是什么 / 未验证项是什么"，避免把"看起来对"当成"证明对" |

这套方式的效果：整项目没有出现"推翻重做"级别的返工，最长的返工是一条算法级（局部自适应背景）—— 上线后实测无收益，整版回退，成本约一天。

## 1 提示词怎么写才有效

有效的五类写法（均在项目里实际使用过）：

| 写法 | 示例 | 为什么有效 |
|---|---|---|
| **限定读者与用途** | "这份文档的读者是拿到压缩包的人，他要能照着做出来，不许出现只有你知道的路径" | 直接把验收标准写进任务，避免产出面向内部的自证材料 |
| **要求先给判据再给方案** | "先说这一步能确定什么、把哪两种可能分开，再讲怎么做" | 阻止大模型跳到实现细节，先收敛诊断空间 |
| **要求量化代价** | "改这一处要动几个文件、要不要重编、耗时多久、影响多少像素" | 迫使把"优化"折算成可比较的数字，而不是形容词 |
| **禁止无证据的归因** | "任何不是你实测的结论，标明是推算还是实测" | 消除"编造合理故事"的倾向 |
| **要求可执行的失败分支** | "每步给我：敲什么、等多久、看到什么算成功、失败怎么查" | 交付物从"描述"变成"操作手册" |

反模式的四类写法（同样实际踩过）：

1. **只给目标不给边界**（"帮我把这个做出来"）—— 大模型会自由扩张范围，改动面不可控。
2. **用讨论中的意向当成命令**（"打一拍就行"这类方案性表述）—— 会被当成开工许可，产生未经确认的改动。
3. **只报现象不报数据**（"画面不对"）—— 会得到一串基于猜测的"再试一次"，而不是定位。
4. **问"哪个更好"而不给代价函数**（"A 还是 B"）—— 会得到两面都说好的答案。

## 2 大模型给出的错误建议及处置

以下每一条都是实际发生、实际被数据或源码推翻的。保留它们是本文件最有价值的部分——**这些错误在同类项目里会重复出现**。

| # | 大模型的建议 | 错在哪 | 怎么发现的 | 最终做法 |
|---|---|---|---|---|
| 1 | "VDMA 的 `tready`→`tdata` 之间隔着 DDR 读延迟，因此必须自己加一个深层队列来吸收相位差" | 忽略了 VDMA 内部有行缓冲：被反压期间它继续把数据取进内部缓冲、灌满即停，队首 beat 一直摆在总线上等 `tready` 放开 | 改用"紧反压 1:1"后实测数据当拍即到，队列完全不需要 | 去掉队列，改紧反压 + 帧首锚定 |
| 2 | "两路数据配不齐就加大缓冲深度" | 节拍/相位问题不能用容量治；诊断计数本身被计数 bug 污染时，"差几万像素"的数字越稳定越误导 | 缓冲从 8192 加到 131072，实测毫无改善 | 改为"不丢像素的锚定式对齐" |
| 3 | "每帧清空配对队列即可自动重对齐" | 清空 = 每帧丢一批已读数据 ⇒ 相位每帧滑一次（实测 8192 像素 = 8 行 + 416 列 ⇒ 整幅上滚 + 竖缝） | 板上画面持续滚动，配合 FIFO 峰值占用读数定位 | 改为帧首锚定，**绝不丢像素** |
| 4 | "让两路各自从帧首数 0,1,2…，计数相等即对齐" | 两路存在固定超前量，每到帧边界必然一方已归零、另一方还剩几十万 ⇒ 永久卡死 | 单元 testbench 超时把死锁直接暴露 | 改为锁存帧首 + 绝对计数 |
| 5 | "每个目标只跑一次分类，把结果缓存起来" | "只算一次"的隐藏前提是"那一次发生在目标形态稳定之后"；手仍在画面上时，掩膜是"手 + 物体"的合并块 | 实践方指出遮挡会污染首帧样本 | 改为每帧轮转识别 + 最近 5 次多数投票 |
| 6 | "等画面稳定再分类"（对上一条的补救） | 稳定判据在实机上抓不准：框每帧都有微小变化，反而更难调 | 现场试验失败 | 回到"勤算 + 平滑显示" |
| 7 | "不做定位、整幅缩放后直接推理" | 64×64 输入下，972×720 整幅是 15 倍缩小，目标不足 1 像素 | 按尺度直接推算即证伪 | 背景差分定位 + 目标级推理（见报告 5.5） |
| 8 | "把参考电平按帧首锁存，避免中途改参数造成撕裂" | 该量是逐像素变化的（背景均值），锁存后整帧只用帧首那一个值 | 集成测试全帧判定作废 | 逐帧常量才锁存，逐像素量必须直通 |
| 9 | "屏蔽无效区就把 valid 压掉" | 下游按"有效拍"计数（行缓存列计数），压 valid 会改变每行拍数 ⇒ 行结构整体错位 | 集成测试成片错位 | 改在数据/判据侧压制，valid 原样透传 |
| 10 | "把 `C_VTG_MASTER_SLAVE` 的从/主关系按常规理解接" | 主从接反会与 VTC 的 `gen_clken` 形成互等死锁，显示侧一帧都不收 | 该 IP 的 `status` / `sof_state_out` 长时间不动 | 改 Slave、断开互锁线、使能接常量 |
| 11 | "PL 侧通过导出 profile 之类的数据看" | 无硬件活动文件时只能做向量无关估算，置信度 Low | 功耗报告自身标注 Confidence Level = Low | 报告里明确标注为估算，并给出补测方式 |
| 12 | "用 `Get-Content` 回读文件确认中文是否正确" | 该命令按本地代码页解码 UTF-8，必然乱码，会得出"文件损坏"的**假警报** | 换工具读取后文件完全正常 | 判断文件内容一律用能指定编码的读取方式 |

**共性规律**：大模型的错误几乎都集中在**"把某个未经核实的器件行为当成物理定律"**和**"把某个前提省掉"**两类。处置办法只有两条：**回到源码/数据手册核实器件行为**；**把结论依赖的前提逐条列出来验证**。

## 3 自我纠错轨迹（三次典型）

### 3.1 时序"没效果"——其实是切错了位置

- **判断**：为抢时序给某级插了流水寄存器，综合后全局 WNS 只变化 0.011 ns，判定"打拍无效"。
- **自我纠错**：按 Path Group 分域重解，发现真正的关键路径起点是**配置寄存器**、走向是比较器 → 显示 MUX → 输出，根本不经过被改动的那一级。
- **教训**：**全局 WNS 是所有时钟域的最小值，不等于你那个域的余量**；看时序的第一步是按 Path Group 拆表。

### 3.2 "加光没效果"——其实是自动曝光在补偿

- **判断**：加光后画面上看不出变化，一度归因为"光源无效"。
- **自我纠错**：把 AEC 与 AGC 切手动、固定曝光与增益后再对比，同参数下平均亮度提升约 38 倍。
- **教训**：排查"某个调整没效果"时，先问"是否有自动控制环节把它补偿掉了"。

### 3.3 新代码"没进位流"——编译成功不等于逻辑生效

- **判断**：改了自研模块后构建成功、位流也生成了，但资源占用与改动前完全一致。
- **自我纠错**：查该模块的离体综合（OOC）日志，时间戳仍是上一轮、利用率里 Slice LUTs 只有 2 个——那是透传骨架。
- **根因**：块设计中 `module_ref` 单独跑离体综合，只重置顶层 run 不会重置它。
- **教训**：**必须有一条能证明"新逻辑真的进去了"的判据**——这里就是"OOC 资源必须变化"。

## 4 验证与判别：把"看起来对"变成"证明对"

| 手段 | 用法 | 实例 |
|---|---|---|
| **黄金参考** | PC 端逐位复刻目标语义的 numpy 实现，与硬件输出逐字节比对 | int8 CNN 的五层张量与 logits，`mismatch = 0` |
| **数量不变式** | 不只比数值，还比"到底传了多少个" | 30 帧 × 每帧像素数 = 20 995 200，任何错配都露出来 |
| **逐级不变量普查** | 每级挂"有效拍数 / 行尾次数"计数器 | 五级都是 2128 拍 / 56 行，问题一次锁定到最后一级 |
| **偏移搜索** | 扫延迟 d=0..20，找错误数归零的那个 d | 一次同时证明算法正确与真实流水延迟 |
| **三明治 A/B/A** | 测 A → 测 B → 再测 A，用两次 A 的差判定漂移 | 排除"场景自己变了"导致的假结论 |
| **降低规模的反向检查** | 缩小仿真规模时检查参数是否仍落在同类约束里 | 小规模仿真的行字节数恰好是 8 的倍数，因此**掩盖**了一个只在真实宽度下出现的错位 |
| **判据自检** | 每个判据都要能回答"它在什么情况下会打印失败" | 曾有三个计数器从未被赋值，恒打印 0，"全部通过"是假的 |

原则：**先问"它失败时会打印什么"，再问"我改了它会不会变"**。说不出来 ⇒ 这个判据没在判。

## 5 工具链使用：AMD ROSS 技能包与 Vivado MCP

| 工具 | 用途 | 实际产出 |
|---|---|---|
| AMD ROSS 技能包（`Xilinx/ross-ai-assistant`，2026.9.1） | 提供 Vivado 侧的标准检查流程与每条违规规则的修复模板 | 方法学检查、RTL lint 均按其流程执行 |
| Vivado MCP 服务器（2026.9.1） | 常驻 Vivado 会话，工程查询与综合/实现驱动 | 一次开工程、多条查询连跑，避免每次重开工程 |
| `report_methodology` | UG906 方法学检查 | 检查项 0 违规 |
| `synth_design -lint` | RTL lint（2026.1 起输出 CSV） | 15 条 warning / 0 critical / 0 error，逐条比对修复模板后确认均可豁免或有意保留 |

使用体会（对后续项目可复用）：

1. **技能包的价值在"正文里的禁用清单"**，不在目录。它明确写了"不要用 batch 模式跑 Vivado"，而这条正是最容易违反的。
2. **MCP 的价值在"常驻会话"**：批处理每次都要重开工程（15~20 秒），交互式排障时差距被放大。
3. **合规性检查要绑在流程节拍上**：每加一级新逻辑就重跑一次检查，否则会在旧代码上得出"全部通过"的结论。
4. **检查结果要当成待解释项而不是分数**：15 条 warning 里只有 3 条来自本项目的代码，其余来自工程内其他模块的既定实现。

## 6 可复用结论

1. **约束的密度决定产出的质量**：把"不可让步的边界 + 每步判据 + 失败分支"三样写清，产出的返工率显著低于只给目标。
2. **让大模型自己给出前提，再逐条打掉**：错误结论的根因基本都是某个被默认成立的前提。
3. **器件行为必须回源码/手册核实**：本项目最大的两次弯路（配对队列、行字节数错位）都源于"按常识推断器件行为"。
4. **每条结论都要有可复核的凭据**：源码行号、寄存器回读、仿真输出、板上毫秒数，四者之一。
5. **保留失败记录**：本文件第 2 节的 12 条错误建议，比任何一条成功经验都更能防止同类项目重复踩坑。
